# Real development tasks

These optional experiments use pinned public source and locally restored dependencies. They cover complete one-shot tasks and bounded two/three-user-prompt tasks with identical final requirements. They are not a live-model CI gate or a statistical claim about every model/repository. Run the [conversation runner](../../../scripts/measure-navlyn-conversation.mjs) as described in the [workflow](../../navlyn-development-workflow.md). Use a fresh output directory, retain failures, and do not run other builds/tests during task timing.

The model sees a fresh source export and the task prompts, not this review guide, upstream patches or injected acceptance tests. Integrity validation checks report structure and evidence locations only. Review reports independently against the selected source and implementation; a plausible conclusion without the requested evidence is incomplete. Time, cumulative input, uncached input, retries, tool choice and completion quality all matter. Source-readable complexity is still a valid coexistence case, not proof that semantic analysis was needed.

Completed/expired turn metrics are saved before optional Git artifact capture. Large locally installed package/tool trees can exceed the bounded capture buffer; captureError and partial diff identify incomplete snapshots while preserving the original workspace and continuing independent cells. This is a harness artifact failure, separate from task completion or correctness. Do detailed trace parsing after a cell ends to avoid observation costs affecting timed work.

| Task | Independent review criteria |
| --- | --- |
| `gcm-authtype` | Twelve injected offline behavioral cases plus affected existing tests: capability negotiation, compatibility of old response APIs, strict ephemeral parsing/output, typed versus legacy output, empty supplied credential, store validation, continuation/state and secret redaction. Inspect extra provider edits and test scope separately; no new authentication-flow success is implied. |
| `navlyn-paging-impact` | Four production resolver callers at the pinned baseline: CLI `OutlineCommand`, `BatchCommand`, `FuzzyDiscoveryResolver`, direct MCP runner. Explain current late MCP projection, external adapter forwarding, unpaged defaults, exact C#/VB totals/order, candidate identity/registration, request-local isolation, limits and cancellation. Omitting batch/fuzzy paths makes the impact review incomplete. |
| `monogame-resource-lifetime` | List removal under `_resourcesLock` is linear; repeated removals can dominate CPU work. Follow the same weak-reference instance through ownership/reassignment, disposal and finalization. Keep weak ownership and examine locking. Device disposal uses a snapshot because disposal mutates the collection; reset traversal and platform partials also need review. Observed insertion order alone does not prove a required ordering contract. Releasing a lock around callbacks needs ownership/race analysis. CPU tests need a registry seam/hook rather than assuming a normal graphics-device constructor is headless. A hash set offers expected constant-time removal, not guaranteed GPU/end-to-end improvement. |
| `eshop-price-propagation` | Both versioned entrypoints, EF modified/original price, local catalog/outbox transaction and publish state; event-name/type routing and actual registrations. Basket has no product-price subscription; the Webhooks price handler is a no-op. Basket gRPC exposes product/quantity, while WebApp fetches prices from Catalog and caches its basket state: changing persisted basket price alone is insufficient for that UI. RabbitMQ catches handler/deserialization exceptions and subsequently acknowledges. Distinguish local/distributed atomicity, publication/consumer effects and static/runtime proof. Propose a complete basket/UI path with failure handling/tests. |
| `gcm-broker-dependency` | Actual MSAL 4.85.2 selected methods and local PE provenance. `WithBroker(BrokerOptions)` sets dependency configuration and runtime support; `IsBrokerAvailable` probes availability rather than resetting configuration. The constructor stores enabled OS flags; `None` disables the configured OS state. A caller-only flag cannot undo builder mutations, and the cached builder preserves them. Cover platform/session gates, repeated use and uncertainty in uninspected internal/runtime paths. Comments, method names or an unrelated overload alone do not satisfy the task. |
| `monogame-reset-context` | DesktopGL/net8.0 compile items and constants include OpenGL partials and exclude DirectX/Web/native alternatives. `PlatformReset` has no implementing partial in this compilation; the DirectX implementation is not DesktopGL evidence. Public Reset raises events/presentation updates without calling GraphicsDevice.OnDeviceResetting's no-argument resource walk. The direct Android context-loss caller is excluded from DesktopGL; similarly named GraphicsDeviceManager event hooks take event arguments and are different symbols. No active in-project DesktopGL caller of the no-argument walk is established: the proposed rationale is false, but this does not establish a current DesktopGL runtime regression or CPU saving. Deleting shared code must account for Android and external/friend/reflection callers. In-project resource overrides are Texture, RenderTarget2D, Shader, Effect, VertexBuffer and IndexBuffer; DirectX state overrides are excluded. Follow concrete platform bodies rather than assuming identical cleanup (OpenGL RenderTarget2D's hook is empty, Effect clears constant buffers). Examine actual call sites, weak ownership, disposed/null targets and callback traversal/locking; an in-project override list is not proof about arbitrary application subclasses or GPU outcomes. Distinguish a repair plan from tested behavior. |

Difficulty depends on relationships, ownership, project/context boundaries and required evidence, rather than file or changed-line counts alone. Preserve both one-shot and short-conversation observations; do not convert one workflow into the sole definition of product success. The game/web/library investigations produce plans and evidence, while the application protocol task also implements and executes offline tests. Compare conditions within the same task, not the elapsed time of unlike tasks.

Review intermediate turns against the requirements actually issued at that point, then review the final result against the common complete-task acceptance. An investigation-only first prompt is not expected to contain an implementation requested in a later prompt. Retain rework and changes of evidence/context across turns. Each recorded task specifies a per-turn timeout: conversations can have a larger total allowance than one-shot, so an expiry is bounded-completion evidence, not proof the same task could never finish with more time. Do not count unequal-correctness/unfinished pairs as strict equal-quality latency wins or extend limits retrospectively to erase a failure.
