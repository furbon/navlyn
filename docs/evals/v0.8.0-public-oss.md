For each supported case, the fresh CLI result was measured three times after one warmup in separate processes. The returned JSON was identical across those three runs. A single MCP server also resolved the same position three times after a warmup. For the direct MCP cache path, three outline/read warmup pairs preceded 20 measured pairs. The warm figures were rerun after the final reference and restore-assets freshness repair; the fresh CLI figures were measured after the earlier missing-SDK diagnostic repair, which this MCP-only change did not affect. Every supported case stayed below the previously fixed 158.72 ms outline and 153.30 ms read p95 limits. Historical execution model: MCP `navlyn_target` used a CLI process per call in this v0.8.0 evaluation, so its latency was not included in the direct cache limit. See the current architecture guide for the present execution path. The fresh CLI p95 values include process and workspace startup.

The projects were restored with a nuget.org-only configuration and evaluated without running their builds. Child processes had isolated homes and package caches, with credential-bearing environment variables removed. This Windows host had no container or WSL boundary; MSBuild design-time evaluation and package targets still ran with the current user's file access. Before loading, selected project imports and executable targets were reviewed. Dapper and xUnit needed full Git history for Nerdbank.GitVersioning. xUnit also needed its pinned `assert.xunit` submodule at `2fe0bb3f20e0179cd58486b6ef4f6322cf2ccf47` to supply linked source files.

S8 was kept as a source-only observation: its selected bindings project references a native project with Emscripten imports and a Zig `Exec` target. The generated file contains `public static extern Vec2 AABBCenter(AABB a)`, but no Navlyn semantic pass is claimed. S9 requires .NET SDK `11.0.100-preview.5.26302.115` and an Arcade beta SDK that were unavailable on the test host. Both cases remain in the nine-case denominator.

The xUnit run found and drove a correction to `symbol-info`: a primary-constructor parameter now reports its constructor as `containingSymbol`, with the source file and caller-parameter attributes intact. Dapper emits upstream duplicate additional-file warnings, and xUnit emits an unmatched project-reference warning; neither warning changed the selected source symbol.
