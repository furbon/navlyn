Reviewed on 2026-10-04 against released main `8a28973924ef7c09ad1d02db24a4efdc9fdab8d8`, retained CI/product evidence, and the actual agent call traces. Findings below distinguish shipped results, observed defects, hypotheses, and subsequent local corrections. Passing tests and publishing packages do not establish that adopting Navlyn helps an agent.

## Where my assessment and execution fell short

The main product claim is efficient, reliable semantic investigation for agents. The experiment supplied no adoption benefit: the same three questions/edits were correct with ordinary tools, while forced Navlyn use consumed 2.04x task time, 3.49x accumulated input, and 2.35x input after subtracting cached input. I previously treated successful functional execution as usefulness and gave internal latency and test counts too much weight. That assessment was unjustified. The experiment cannot establish that Navlyn is harmful on every repository, but it exposes a serious failure for an easy and common class of work.

I reduced discovery by only 4.7%, while leaving 25 tools and 113,329 characters advertised together. The public capture contains 58,119 input-schema characters, 41,125 output-schema characters, and 8,702 tool-description characters. The same 1,645-character output envelope appears for every tool. This is a server payload measurement; how much a client injects into model context must be measured separately. SDK 2 and discovery-first negotiation did not by themselves make the tool definitions cheap.

The routing entrypoint was 6,868 characters; its two references brought the total to 25,282. Its description activated before any repository action for a broad capability list. Its instructions overconstrained first actions and could stop an unfinished task when an outline was clipped. Existing tests enforced a minimum of 700 words and a 32-row, nine-column matrix, plus exact prose. Those checks rewarded a document shape and obstructed simplification. Removing two scoring test classes in v0.8.7 did not remove this remaining problem.

The live comparison itself forced MCP use and forbade it in baseline. It did not test freely chosen hybrid routing or isolate the skill. There were only three tasks, one attempt per condition, on a tiny fixture. The investigation correctness predicates were weaker than exact oracles, though the retained final answers were correct. I should have reported those limits at the same prominence as the results. A larger mandatory campaign would not repair the experimental design.

The migration also left an obsolete package-validator XML lookup, caught after the first integrated CI product suite passed. An early check against the new packed layout would have avoided that failed delivery check. Some local validation began before migrated fixture/golden expectations were reconciled. Later focused reruns were appropriate, but preventable integration failures and excess investigation output still consumed time. Future work must reuse valid evidence and check the changed delivery boundary early.

## Confirmed sources of overhead

1. **Discovery:** the full tool surface is always listed. Deprecated `--tool-profile` values are accepted and ignored; they provide no size reduction.
2. **Search friction:** the traces contain three empty `Client.Number`, `Formatter.Format`, or `IFormatter.Format` lookups. Fuzzy discovery initially matches simple declaration names. The fallback action says to broaden the query but repeats the same query and supplies no containing-type constraint. Supporting qualified intent must retain overload/context ambiguity, not silently fall back to an unrelated simple name.
3. **Invalid combinations:** source-position target selection received fuzzy selection options; implementations received `scope`. Both were rejected correctly, but each caused another model turn. Long prose on a broad optional-parameter schema is insufficient to steer valid combinations reliably.
4. **Unnecessary breadth:** a literal-only overload-body change invoked impact; the interface task invoked broad impact, then outline, relationships, and a signature read. Some facts and targets were reacquired. The traces show expensive choices; they do not prove which instruction caused each choice.
5. **Response duplication:** symbol facts, selectors, reproductions, and next actions repeat within responses. The MCP wrapper also copies the result into text and structured content. The latter follows [MCP 2025-06-18 compatibility guidance](https://modelcontextprotocol.io/specification/2025-06-18/server/tools#structured-content); removing it universally is not a justified shortcut. Reduce the canonical payload first and verify client rendering separately.
6. **Mismatch of measurements:** millisecond warm server execution does not capture discovery, cold workspace load, model reasoning, repeated turns, text reads, or edit verification. These costs determine whether adoption helps.

The correct coexistence model lets ordinary tools complete simple work and brings in compiler facts when uncertainty or requested completeness justifies them. File size alone cannot decide this: a short linked or conditionally compiled file can still need semantic context, while a literal change in a large file may not.

## Additional defects and gaps found in this review

| Finding | Evidence and implication | Treatment |
| --- | --- | --- |
| Skill upgrades reject recent releases | `install-routing-skill.ps1` accepted current release and versions through 0.8.4, omitting 0.8.5/6/7. Existing lifecycle coverage checked only 0.8.0/1. An added real lifecycle case failed upgrading from 0.8.5 before the fix. | Fixed locally; verified repository and user layouts for 0.8.5/6/7 as well. Include released 0.9.0 for the next version. |
| PR follow-up test selection misses shared inputs | CI class selection recognizes `*Tests.cs` and `TestSupport`, but misses `Mcp/TemporaryDirectoryCleanup.cs`, `GlobalUsings.cs`, and skill files read by tests. Exact-main is full, so the release passed, but a follow-up PR can have insufficient selected coverage. | v0.9.1 task: conservative shared-input fallback and explicit cheap skill coverage. |
| Publication budget has insufficient headroom | Orchestration serially waits up to 600 seconds per package; the workflow allows 20 minutes for the entire job, including setup, observations, push, and retained journals. Actual v0.9.0 indexing dominated roughly 13 minutes of publication. | v0.9.1 task: one explicit overall polling budget and overlap indexing waits while preserving intent journals. Do not blindly retry uncertain pushes. |
| Published package lookup can be negatively cached | The MCP tool update required `--no-http-cache` after public availability was verified. | Document and verify a targeted retry; avoid global cache clearing. |
| Setup filename needed a manual release correction | The manifest uses `navlyn-setup.zip`; installation guidance uses the versioned filename. Both aliases were eventually published. | Automate the required names and verify uploaded bytes against the manifest. |
| Semantic aliases do not constrain type kind | Class/interface/record hints normalize to NamedType; the independent type-kind filter was deferred. | Add a separate explicit filter, with shared resolver semantics, rather than redefining existing aliases. |
| Larger-scale benefit and resource bounds are unproven | Tiny warm benchmarks and a 120-file corpus do not measure full agent tasks or realistic memory/input-inventory costs. | Measure targeted larger workloads; profile before optimizing or adding daemon machinery. |

These findings are not a claim that every remaining defect has been found. The next plan includes independent audits of selection, scope, freshness, concurrent lifetimes, errors, packaging, and platform behavior alongside agent cost.

## Corrections completed locally during this review

- Revised the usefulness claim and distinguished three tasks from six executions; added aggregate token/time figures and experimental limitations.
- Rewrote the routing skill around actual uncertainty and ordinary-tool coexistence. Removed compulsory preambles, the clipped-outline stopping rule, and the stale-ID validation detour. Retained ambiguity, framework, freshness, and static-evidence boundaries.
- Reduced the skill from 6,868 to 3,990 characters and all three resources from 25,282 to 8,812 (about 65% smaller). Supporting references are conditional. These are character counts for ASCII text, not measured token savings.
- Replaced prose/word-count/table-shape tests with metadata, installed-reference, and registered-tool checks; repaired the skill-upgrade allowlist and exercised recent-release upgrade cases.

Verification: solution build passed with zero warnings/errors, five focused xUnit cases passed, C# BOM/CRLF checks passed, the skill validator passed, and the installer lifecycle passed in repository/user layouts including conflict preservation and path containment. Runtime product code was not changed; the previously successful 699-test release evidence is not relabeled as a new run. No new free-choice agent trial has been performed, so the adoption-cost defect remains open. These local changes are not a published v0.9.1 release.
