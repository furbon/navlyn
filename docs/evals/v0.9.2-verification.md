# v0.9.2 verification and product evidence

Recorded 2026-10-04. Baseline: released 0.9.1 at `b6e7ba85b35d5cd201f1d853ed294be258dbaf45`. Candidate: the 0.9.2 changes on `codex/v092-verification`, measured before commit. Previous unfavorable results remain in [0.9.1 evidence](v0.9.1-product-evidence.md). This investigation establishes a useful CLI adoption path and an equivalent-output backend improvement; **it does not establish universal adoption benefit or consistently beneficial MCP selection**.

## Answers to the four questions

1. **Costs can be separated enough to act.** Actual request events and optional server stages distinguish discovery, tool intervals, cold workspace establishment, content-sensitive input validation, resolution/enrichment and response handling. Most elapsed agent-task time is outside observed tool intervals. That remainder includes model/client/transport/startup/gaps, not pure inference time. Token usage is observed separately; character count is not a token estimate.
2. **An equivalent shorter route wins in a defined task.** For an overloaded referenced DLL, the optional CLI's single bound-body read gives the required implementation evidence. Both paired candidate attempts are correct and reduce elapsed time, cumulative input, uncached input and exchanges versus ordinary tools. The read capability already existed in 0.9.1: this is an integration/routing improvement, not a new decompiler algorithm. Backend outline paging also improves while returning identical requested facts.
3. **Unforced selection remains imperfect.** CLI and MCP availability were evaluated separately, with ordinary tools allowed and no compulsory Navlyn/skill use. Config tasks all used ordinary reading. Readable-source relationships also used ordinary tools, but unnecessary skill reads remain. MCP used a bound read in the first two binary attempts; a final schema follow-up used it in only one of two. Availability and smaller discovery do not guarantee appropriate selection.
4. **The product boundary is conditional.** Start with ordinary reads/search for clear source facts. Offer occasional semantic investigation through a short CLI recipe; use persistent MCP for repeated compiler-context questions where session reuse matters. This investigation supports that strategy, not a mandate to put a skill and persistent server into every task. Broad multi-repository/model evaluation and repeated-session agent benefits remain unestablished.

These findings rule out treating the observed costs as an already-proven fatal Roslyn limitation. They also rule out claiming that 0.9.2 removes every adoption disadvantage. Cold compiler context and truthful freshness have real costs; unnecessary acquisition, late limits and excessive instructions are implementation/integration choices.

## Method and retained evidence

Windows, .NET SDK 10.0.401, Node v24.18.0, Codex CLI 0.160.0, `gpt-5.5`, medium reasoning. One ephemeral client per task, sequential condition rotation across attempts, unrelated configured MCP servers disabled. Isolated repositories were restored before timing. Producer source/PDB were outside the consumer workspace and unavailable to the model. Ordinary tools could use .NET compilation, reflection and IL; they were not artificially handicapped. Timing includes client/server startup and discovery. No build/test/benchmark ran concurrently with the timed model trials.

The model received the same question, source call anchor and answer oracle across conditions. CLI guidance supplied an optional command recipe; MCP offered the focused tools. When requested, the canonical routing skill was available for automatic selection, without mandatory reading. Therefore these compare practical integration packages, not a blinded estimate of only the schema change. Two attempts are observations, not population statistics; prompt caching varies substantially. Input below is cumulative API-reported input across the task. Uncached is input minus reported cached input; neither is a monetary cost calculation.

Raw answers, JSON events, timestamped event arrivals and server stderr remain under ignored `artifacts/review-v092/`. The committed harnesses are [adoption](../../scripts/measure-navlyn-adoption.mjs) and [outline](../../scripts/measure-navlyn-outline.mjs). Fresh output paths prevent overwriting prior attempts. No automatic retries or live-model CI gate are introduced. Original reports remain intact; `derived-summary.json` recomputes interval unions and corrects the earlier skill-read counter for doubled Windows path separators. Initial ordinary binary parameter-type validation rejected the equivalent alias `short`; the baseline report explicitly preserves `initialOracleCorrect: false` and the oracle correction. The final ordinary failure below is an actual wrong arithmetic sign, not that oracle issue.

## Whole-task comparison

The initial public-0.9.1 comparison used minimal availability guidance without the routing skill. All six answers were correct after accepting `short` as `System.Int16`. Config: ordinary 9.038s/27,483 input, CLI-available 8.887s/27,617, MCP-available 9.319s/27,533; none used Navlyn. Binary: ordinary 61.041s/107,052, CLI 27.120s/58,942 (six calls, one Navlyn call), MCP-available 54.373s/74,637 (eight calls, **zero Navlyn calls**). The latter speed cannot be attributed to Navlyn. The first harness prototype failed client configuration before tasks; its evidence is retained separately, not counted as a product result.

The main candidate comparison used the new routing skill and initial discovery envelope. Debug candidate binaries; each semantic call began in a cold session. All twelve config/binary answers were correct.

Config always used one ordinary read, zero Navlyn calls and zero skill reads. Availability adds about 1.3% CLI and 0.9% MCP cumulative input here; timing varies, and no attributable speed improvement is claimed. Cached/uncached variation is large, so a single uncached observation is not a reliable inherent integration cost.

Both CLI binary attempts used exactly one bound-body command and one skill read; total tool calls were 2 and 5 versus 8 and 8 ordinary calls. Elapsed reductions are 63.0% and 70.0%; cumulative input reductions 60.2% and 44.3%; uncached reductions 19.4% and 21.0%. Evidence identifies the compiler-bound `Normalize(short)` body, multiplier 37, offset 211 and checked arithmetic, including negative-value magnitude handling. Ordinary inspection compiles/reflects the consumer and decodes actual DLL IL; it has access to the same evidence class.

Both initial MCP binary attempts used one bound-body call, one skill read, four total calls and a full-profile override. They reduce elapsed time and cumulative input, **but uncached input increases by 21.6% and 28.3%**. This prompted actual schema/default guidance changes, not a claim that MCP had solved every cost.

Observed tool-interval unions are 4.212/4.667s for CLI versus 3.660/3.434s ordinary; outside those intervals 17.546/22.196s versus 55.220/85.974s. Initial MCP tool intervals are 5.286/5.147s, outside 21.546/22.137s. The complete task improves despite a more expensive semantic tool invocation; avoided investigation and exchanges dominate these examples. Interval unions avoid double-counting overlapping commands. They cannot isolate pure model computation or network latency.

## Backend, discovery and memory

Released 0.9.1 applies outline bounds after building detailed facts/candidate identities for the complete file, serializing and building the MCP envelope. Candidate 0.9.2 resolves lightweight semantic headers for exact count/order, then enriches only the requested page. Candidate registration and JSON generation also operate on that page. Default CLI and unpaged full results retain their complete contract. Optional CLI bounds make the same improvement available to external adapters.

The final comparable run uses **Release for both versions**, one shared restored workspace with 1,200 methods (1,202 entries including namespace/type), 100-entry pages at offsets 0/100, actual stdio transport, one cold and three warm requests each. The harness checks expected names/counts/page metadata and deep-equal facts, identity and source bounds against the released binary for all requested entries. Text and structured JSON match. This is a synthetic scaling fixture, not a large-repository adoption trial.

| Observation | Released 0.9.1 | Candidate 0.9.2 |
| --- | ---: | ---: |
| Startup / initialize ms | 469.275 | 475.862 |
| Focused discovery characters | 19,642 | 16,068 |
| First cold page ms | 4,373.299 | 3,333.456 |
| Warm page ms, all three | 530.374 / 333.714 / 252.381 | 80.035 / 65.801 / 47.039 |
| Warm mean ms | 372.156 | 64.292 |
| Server working set after fourth call, bytes | 361,226,240 | 230,850,560 |
| Server private bytes after fourth call | 364,748,800 | 139,853,824 |

Warm mean drops 82.7%; cold drops 23.8%. Requested page payload sizes are equal (55,165/55,651 characters by page), so the backend win is not a smaller-evidence artifact. Discovery drops 18.2%, through focused compact envelope schemas; full surface/profile retain detailed schemas and per-call full remains accepted. Memory is one server-process snapshot, excluding MSBuild children/client/model, with no repeated statistical or leak estimate. Do not generalize it to whole-product peak memory. An earlier Debug-candidate/Release-baseline exploratory run is retained but is not the primary comparison.

### Real-repository diagnostic probe

Before behavior changes, one instrumented Debug 0.9.1 session on Navlyn itself: five projects, 248 indexed documents including new instrumentation. This differs from the released 247-document probe. Initialize 526.508ms, discovery 22.125ms/19,642 characters. Outline cold 5,439.426ms (cache acquisition 3,683ms, MSBuild loads 1,809+1,404ms within acquisition, resolve/build 1,638ms including JSON 15ms). Warm same outline 111.513ms (input captures 70+31ms, resolve 8ms). Warm declaration 84.244ms (captures 29+31ms, resolve 20ms including JSON 7ms); outgoing calls 275.837ms (captures 33+33ms, resolve 206ms). Server stages are inclusive; parent/child values must not be summed.

Cold stabilization expands the input specification to loaded metadata/analyzers/assets, requiring another stable load in this probe. Warm validation re-inventories and hashes complete input contents before acquisition and return. The final instrumentation separates inventory and hashing stages, but deleting a load or switching to timestamps alone has not been justified. Same-length restored-mtime edits must remain detectable. No freshness weakening was implemented.

## Implemented changes and verification scope

- Early semantic outline paging in C#/VB, CLI and both MCP adapter paths, with request-local bounds, exact total/order/candidate identity, unchanged unpaged results and existing output-size limits.
- Smaller focused compact output schema; effective default profile advertised; compact bounded-body sufficiency and direct known-position DLL reading documented.
- Shorter routing instructions and optional CLI integration in English/Japanese setup guides; ordinary readable-source work remains available.
- Optional `NAVLYN_PROFILE_TIMINGS=1` request-local diagnostics on stderr, including discovery, cache queue/acquisition, input inventory/hash, resolution, command JSON, envelope/projection. Stable stderr binding avoids in-process Console redirection. Diagnostic write failures cannot change a successful result.
- A real external-adapter concurrency test exposed MSBuild generated-file contention. Per-server external CLI invocations are now serialized, with queue time inside caller cancellation/deadline and no accidental gate release. Independent cold CLI processes can still contend; this limit is documented. MSBuild can generate files in `obj` even for an investigation command.
- C#/VB page-equivalence tests, actual SDK/stdin transport tests, direct/external concurrent paging and output limits, candidate follow-up, timing isolation/closed writer, queue cancellation/recovery. Small portable CI selections include the new component/transport checks. Managed skill upgrade verification includes 0.9.1.

## Remaining work, ranked by the evidence

1. Reduce inappropriate automatic skill/tool discovery and validate it across more models/repositories without forcing use. Keep the minimal CLI route the default recommendation for occasional investigation. Source-readable work still incurs skill overhead; MCP non-selection remains unreliable.
2. Measure repeated semantic tasks in one persistent MCP session against multiple CLI starts and ordinary tools, including complete task inputs. Warm backend latency alone is insufficient to justify persistent adoption.
3. Measure larger actual repositories, editing/freshness paths, total process-tree memory and concurrent independent clients. Consider coordinated MSBuild establishment only with isolation/cancellation/stale-input tests; the per-server queue is a bounded repair.
4. Optimize inventory/load reuse only with equivalent content-sensitive correctness. Track actual input count/bytes and stages; do not replace source/dependency hashing with weak stat checks or assume Roslyn replacement is required.
5. Extend scenarios where binding/configuration removes substantial uncertainty: overloads, partial/generated declarations, multi-target contexts, reference assemblies and cross-project relationships. Preserve ambiguity, scope, warnings and negative evidence.

The useful result is conditional and measurable: optional bound-body CLI investigation wins the measured correct tasks; early paging preserves evidence while reducing backend work. MCP and readable-source integration still have limitations. A claim that adoption always wins, or that the product's entire purpose is now fulfilled, would exceed this evidence.
