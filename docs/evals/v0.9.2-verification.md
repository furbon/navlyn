# v0.9.2 verification: real task results, repairs and limits

Recorded 2026-10-04. Baseline: released 0.9.1 at `b6e7ba85b35d5cd201f1d853ed294be258dbaf45`. Candidate: the 0.9.2 changes on `codex/v092-verification`; each campaign records its binary/source provenance. Previous unfavorable results remain in [0.9.1 evidence](v0.9.1-product-evidence.md). The bounded investigation now includes real game, library, web and application work, complete one-shot tasks and two/three-user-prompt sessions. Both workflows remain product requirements; the small initial cases are secondary diagnostics. See the [evaluation requirements](../plans/v0.9.2-verification.md).

**Concrete improvements are verified, but consistent whole-task wins are not.** The final equivalent-output outline comparison improves warm mean 74.9%. In the real MSAL review, both completed two-turn conditions meet the same acceptance; MCP cumulative input is 8.7% lower with essentially unchanged time and uncached input. MCP completes the one-shot within the declared bound while ordinary expires, an unequal-completion observation rather than an equal-quality latency win. The repaired MCP one-shot is slower than its earlier successful MCP attempt, and optional CLI expires in both workflows.

Source-readable complex tasks correctly use ordinary tools. Their measured input differences expose adoption costs: the Web MCP-available one-shot uses 30.4% more cumulative input despite zero semantic calls. There is no evidence here that Roslyn makes the product purpose impossible; there is evidence of remaining integration and dependency-follow-through gaps. No-call source tasks are not semantic-backend losses, and no-call faster tasks are not semantic-backend wins. The remaining work below follows actual traces rather than replacing one-shot with conversations or requiring Navlyn use.

## Preliminary answers, limited to the diagnostic cases

1. **Costs can be separated enough to act.** Actual request events and optional server stages distinguish discovery, tool intervals, cold workspace establishment, content-sensitive input validation, resolution/enrichment and response handling. Most elapsed agent-task time is outside observed tool intervals. That remainder includes model/client/transport/startup/gaps, not pure inference time. Token usage is observed separately; character count is not a token estimate.
2. **An equivalent shorter route wins in a defined task.** For an overloaded referenced DLL, the optional CLI's single bound-body read gives the required implementation evidence. Both paired candidate attempts are correct and reduce elapsed time, cumulative input, uncached input and exchanges versus ordinary tools. The read capability already existed in 0.9.1: this is an integration/routing improvement, not a new decompiler algorithm. Backend outline paging also improves while returning identical requested facts.
3. **Unforced selection remains imperfect.** CLI and MCP availability were evaluated separately, with ordinary tools allowed and no compulsory Navlyn/skill use. Config tasks all used ordinary reading. Readable-source relationships also used ordinary tools, but unnecessary skill reads remain. MCP used a bound read in the first two binary attempts; a final schema follow-up used it in only one of two. Availability and smaller discovery do not guarantee appropriate selection.
4. **The product boundary is conditional.** Start with ordinary reads/search for clear source facts. Offer occasional semantic investigation through a short CLI recipe; use persistent MCP for repeated compiler-context questions where session reuse matters. This investigation supports that strategy, not a mandate to put a skill and persistent server into every task. Broad multi-repository/model evaluation and repeated-session agent benefits remain unestablished.

These findings rule out treating the observed costs as an already-proven fatal Roslyn limitation. They also rule out claiming that 0.9.2 removes every adoption disadvantage. Cold compiler context and truthful freshness have real costs; unnecessary acquisition, late limits and excessive instructions are implementation/integration choices.

## Method and retained evidence

Windows, .NET SDK 10.0.401, Node v24.18.0, Codex CLI 0.160.0, `gpt-5.5`, medium reasoning. One ephemeral client per task, sequential condition rotation across attempts, unrelated configured MCP servers disabled. Isolated repositories were restored before timing. Producer source/PDB were outside the consumer workspace and unavailable to the model. Ordinary tools could use .NET compilation, reflection and IL; they were not artificially handicapped. Timing includes client/server startup and discovery. No build/test/benchmark ran concurrently with the timed model trials.

The model received the same question, source call anchor and answer oracle across conditions. CLI guidance supplied an optional command recipe; MCP offered the focused tools. When requested, the canonical routing skill was available for automatic selection, without mandatory reading. Therefore these compare practical integration packages, not a blinded estimate of only the schema change. Two attempts are observations, not population statistics; prompt caching varies substantially. Input below is cumulative API-reported input across the task. Uncached is input minus reported cached input; neither is a monetary cost calculation.

Raw answers, JSON events, timestamped event arrivals and server stderr remain under ignored `artifacts/review-v092/`. The committed harnesses are [adoption](../../scripts/measure-navlyn-adoption.mjs) and [outline](../../scripts/measure-navlyn-outline.mjs). Fresh output paths prevent overwriting prior attempts. No automatic retries or live-model CI gate are introduced. Original reports remain intact; `derived-summary.json` recomputes interval unions and corrects the earlier skill-read counter for doubled Windows path separators. Candidate 0.9.2 resolves lightweight semantic headers for exact count/order, then enriches only the requested page. Candidate registration and JSON generation also operate on that page. Default CLI and unpaged full results retain their complete contract. Optional CLI bounds make the same improvement available to external adapters.

The final comparable run uses **Release for both versions**, one shared restored workspace with 1,200 methods (1,202 entries including namespace/type), 100-entry pages at offsets 0/100, actual stdio transport, one cold and three warm requests each. ## Adverse-trace causes and follow-up repairs

The ordinary binary sign error followed two failed assembly-loading approaches and a successful collectible load-context inspection. Its final raw IL contained a conditional absolute-value branch, `ldc.i4.s 37`, checked multiplication and checked addition; the final answer nevertheless reported -37. The operand is positive in the observed bytes. Misinterpreting the conditional `neg` as the coefficient is consistent with the failure, but hidden model reasoning was not observed. A correct ordinary follow-up decoded offsets and branches explicitly. Navlyn already returns a bound decompiled body; the repair therefore improves direct routing and interpretation guidance rather than inventing a new decompiler. New trusted-fixture tests recompile the returned body and compare negative/zero/positive inputs and short extrema against an independent arithmetic expression, including a genuinely negative coefficient and checked overflow. Arbitrary dependencies are not executed as an inspection shortcut.

Input growth has several observed contributors. Initial full MCP text was 2,874/3,006 characters, versus 2,033 in the later compact read; the complete bounded body is retained. Skill reads were roughly 3,000 characters. Known-position runs still performed file inventories, project/SDK discovery, unrelated source reads or extra IL scripts. Extra exchanges repeat conversation context. These observations justify compact defaults, smaller discovery, tighter skill activation and a short MCP initialization recipe that skips unrelated preparation. They do not assign an exact number of API tokens to each field: the client records both text and structured JSON, but whether/how both enter model context was not observed. Prompt-cache differences also affect uncached totals. Keep interoperable text/structured results instead of silently removing one copy.

The server now supplies a short MCP `instructions` hint; an actual SDK handshake verifies the field. Its effect on a particular model is evaluated through task traces, not assumed. The skill description now targets unavailable dependency bodies, unresolved binding/context and uncertain relationship completeness; merely encountering C#/VB source does not require loading it. A no-call outcome is desirable when ordinary tools supply sufficient evidence. A missed useful semantic shortcut, needless skill read or unsuccessful setup is a different issue and is recorded separately.

### Real dependency trace and implemented repairs

The first MSAL review completed its one-shot in 278.606 seconds with 891,470 cumulative input / 72,014 uncached and twenty MCP calls. The first conversation turn expired at the declared 360-second bound; the second prompt was never reached. These remain adverse observations, not discarded attempts. The trace shows repeated constructor/type body failures, empty DLL-internal target searches, unsupported external call-graph requests and additional reflection/IL script failures. Comments alone were insufficient for the task's acceptance.

The repair selects the exact compiler-bound constructor at a C#/VB constructed type token, reports the selected kind/name on body-less errors, includes enum values in metadata declarations, returns the normalized external member documentation ID, and explains that target search/call traversal cover workspace source rather than arbitrary DLL internals. The real GCM build also uses `out/obj/Core/project.assets.json`; the old external reader assumed project-local `obj`. A bounded locator now uses loaded compiler output/generated paths and verifies the assets' project identity, retaining the conventional fallback and content hashes. A reference-versus-implementation fixture with redirected output and a stale conventional assets decoy verifies the actual route. No additional MSBuild evaluation or filesystem-wide search is introduced.

A manual Release read at the real fallback constructor now returns `M:Microsoft.Identity.Client.BrokerOptions.#ctor(Microsoft.Identity.Client.BrokerOptions.OperatingSystems)` and `EnabledOn = enabledOn`; metadata read at the enum token returns `None = 0`. Eleven focused constructor/arithmetic/provenance checks passed before the assets follow-up; nine selected checks including redirected assets passed after it. These are functional fixes; they are not yet a claim that model task time or input improved. The initial failed fixture preparations are retained separately, and corrected checks passed before timing restarted.
