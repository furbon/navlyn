# v0.9.1 product evidence

Measured 2026-10-04 on Windows, .NET 10, using the proposed local 0.9.1 runtime. These are product observations, not a claim that installing Navlyn universally saves time or money. Release CI and public-install evidence are separately available from the release/PR.

## What changed and what is proven

Default MCP discovery exposes four tools instead of 25. Actual `tools/list` is 19,642 characters versus 113,329 in the released 0.9.0 capture: 82.7% smaller. A qualified class target response is 1,694 characters versus 3,330 with a per-call full override; the fixture outline is 9,047 versus 13,806. These are JSON character counts, not model token counts. Full discovery is 122,772 characters: it grew with the new argument constraints and controls. Full mode is an explicit choice, not a size improvement.

Routing now allows ordinary reads, search, and locally clear edits; no compulsory semantic preparation or verification. The three resources shrank from 25,282 normalized characters to 9,247 (the final wording adds focused/full and referenced-body guidance). Metadata/reference/tool tests replace minimum-word-count and table-shape checks. Installer upgrades include 0.8.5/6/7/0.9.0.

Qualified declaration discovery constrains semantic containers without selecting an unrelated homonym, preserving overload ambiguity. Type-kind is a separate filter from NamedType ranking hints. Compact responses retain identity, context, source, freshness, errors, scope and limits; full facts remain available. These capabilities are checked by resolver and actual stdio tests, rather than inferred from payload size.

## Unforced complete tasks

Client: codex-cli 0.160.0; model `gpt-5.5`, medium reasoning, ephemeral sessions. Four tasks × two conditions, one attempt each, sequential counterbalanced order. No Navlyn call is required. Baseline may use file/search/.NET reflection and build tools, including actual local IL. Navlyn condition has the focused MCP server and repository routing skill; unrelated configured MCP servers are disabled. Fixtures are restored before timing, in separate temporary repositories outside Navlyn. Timing includes process startup and discovery. No product tests run during the initial timed comparison.

Task oracles are independent: exact target framework; exact edited source; exact string-overload/interface/direct caller sets; and the DLL's selected short overload, multiplier 37, offset 211, checked arithmetic. The controlled DLL fixture has no source or PDB in the consumer workspace. This is a synthetic task, not evidence about large real repositories. Read the semantic questions as static facts, not runtime execution proof.

The initial baseline passed three of four tasks; Navlyn-available passed four. The baseline DLL answer swapped multiplier and offset. However, **both DLL runs used only ordinary tools**, so the correct answer cannot be attributed to Navlyn. The interface run used four successful MCP calls but was 2.4× slower than baseline and consumed more input. It requested full results and also read the source; qualified queries worked without the old empty-query retries. Easy work made zero MCP calls, yet configuration reading still had startup/context overhead.

One additional DLL pair followed an explicit routing correction: a known call position can use `navlyn_read` with `externalSource: "decompiled"` and `view: "body"`. Same model, reasoning, task and oracle; reversed order, one attempt per condition. Both passed, both again used ordinary tools. The Navlyn-available run was faster, but zero MCP calls and substantial between-attempt variance prevent attributing that difference to Navlyn. Do not retain only this favorable timing. A short release-check script ran during the baseline follow-up; timing is therefore descriptive, not a controlled causal estimate. No more live reruns were performed.

Accumulated input counts repeat conversation context across turns; cached input is reported separately. Different cache hits and model decisions remain confounders. The client traces retain text/structured MCP JSON; this report does not assume the model consumes both copies or translate characters into tokens. No monetary saving is claimed.

A separate deterministic tool probe read the same bound DLL member directly from `Consumer.cs` line 3, column 71: one cold `navlyn_read` returned the exact `Normalize(short)` body, decompiled origin, hashes, checked arithmetic and 37/211 constants in 5,091 ms and 1,919 JSON characters. This verifies the documented shortcut capability; it is not an LLM task or attributable token/time saving. The free-choice trials did not select this route.

## Assessment and release boundary

The release materially reduces the cost of exposing Navlyn and fixes real selection, routing, upgrade, CI-selection, and publication defects. **The complete-task adoption penalty is not demonstrated resolved.** On a tiny readable source fixture, a capable model with ordinary tools remains faster. Even a binary task can be solved with standard reflection/IL tools. Compiler-resolved identity/context and bounded external-member reads remain useful capabilities, but their presence is not evidence of agent benefit without appropriate selection.

End the optimization campaign here. Ship the reduced default and explicit escape hatch with these limits visible. Further work should start from an observed task requiring uncertain project/TFM binding, linked/generated/partial relationships, or a nontrivial external implementation—not another broad tool catalog or mandatory routing chain. One persistent MCP session on this repository (five projects, 247 indexed documents) measured cold summary 3,809 ms and subsequent warm summary/outline/read/navigation at 76/76/70/74 ms. This single-session server check used the full surface for summary availability; it is not a baseline agent comparison or total-memory measurement. Large-workspace latency/memory and real-client deferred discovery are future measurements; no new cache/daemon rewrite or broad compatibility claim is justified by this sample.

## Verification and retained local data

One integrated local run: 718 tests, 717 passed, one obsolete 25-tool default expectation failed. That expectation was changed to four while preserving exact implementation, changed-PE freshness, hash and stale-read assertions; its focused rerun passed. Focused resolver/options/stdio coverage passed, as did portable quick checks and fast release checks. Publication recovery passed 68 cases and orchestration 43, including overlapping delayed indexing without repush. The optional legacy core CLI script still expected ten dual-framework root projects after the .NET 10 migration; all four project-count expectations were corrected to the five actual projects and the core check rerun. Final PR/exact-main CI supplies the authoritative final suite and packaged-consumer checks; no full local suite was repeated after the single correction.

Ignored reproducibility artifacts: `artifacts/review-v091/live/*.jsonl`, answers and `results.json`; `live-followup`; `probe-default.json` / `probe-full.json`; `quick.log`, `quick-portable.log`, and `release-checks.log`. The harness records commands/usage/answers and exact edit oracles. Local temporary paths are omitted from this document. Raw agent traces and exploratory scripts are not committed or shipped in packages.
