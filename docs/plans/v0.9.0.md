# v0.9.0 implementation and release plan

## Outcome

Publish 0.9.0 immediately after 0.8.7 with .NET 10 as the only supported Navlyn runtime, faster focused MCP navigation, smaller discovery output, and measured agent usefulness.

## Work

1. Remove net8.0 tool/test targets, compatibility package branches, runtime lanes, installer fallbacks, and obsolete runtime assertions. Update prerequisites and migration documentation to .NET 10 only. Do not build a backward-compatibility layer.
2. Move focused navigation and target selection variants onto the shared warm workspace execution path. Share typed input validation and selected-symbol execution across CLI/MCP/batch where it removes duplication. Retain content-sensitive freshness and precise project selection.
3. Add explicit target-framework selection to CLI/MCP/batch; stop relying on project display-name suffixes for framework selection. Add an independent type-kind filter if the resulting shared selection model makes it small and useful, without reinterpreting existing symbol-kind aliases.
4. Reduce MCP discovery and result size while retaining useful schemas, current tool names, machine-readable facts, and necessary ambiguity/freshness warnings. Measure bytes and token estimates; do not remove schema guarantees merely to meet an arbitrary size target.
5. Upgrade to MCP SDK 2.x and test the actual stdio negotiation, tool schemas, structured results, cancellation, and existing clients. Avoid adding unrelated HTTP, OAuth, Apps, or Tasks surfaces.
6. Reuse the shortened CI and release pipeline. Add focused coverage only for the new behavior and meaningful regressions; do not restore expensive redundant gates.
7. Run a small fixed live comparison of real investigation/edit tasks with and without Navlyn, using the same model, task, and repository state. Record task correctness, wrong-target edits, elapsed time, calls, and output size honestly. Recheck the existing public corpus through a bounded reproducible runner and retain classified failures.
8. Update English/Japanese installation guidance, supported client evidence, architecture/performance docs, schemas, examples, and changelog. Publish the tested packages, annotated tag, and GitHub release.
9. Review all changed and adjacent behavior throughout the work, including new defects outside planned features. Recheck selection, freshness, output contracts, transports, installation, runtime prerequisites, packaging, CI, publication, and docs together before release; repair root causes and add only meaningful focused coverage.

## Verification and execution order

Migrate runtime targets first, then build and run the fast suite. Implement warm navigation and explicit selection in small units with focused tests. Upgrade the SDK and validate the protocol before live checks. Reuse successful checks unless their inputs changed. Pack once and publish those bytes. The real-task comparison is a small product experiment, not a 108-attempt campaign.

## Self-review

- Full .NET 10 migration is an explicit requirement, including scripts and package smoke, not just project TargetFramework edits.
- Performance work retains correctness and freshness; it must remove independent workspace loads from common loops.
- Discovery reduction is measured against 0.8.6's 118,940-character tools/list result and tested with actual routing.
- The SDK upgrade must be assessed against current stdio use; unrelated breaking changes do not justify extra product features.
- Live results may show no improvement; report the result and improve the actual product rather than changing acceptance scores.
- Both releases require observed public availability and usable installed CLI/MCP commands.
