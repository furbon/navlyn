## Evaluation requirements clarified by the user

- Use actual repositories and plausible daily game, library, web and application-development work. Account for codebase size, project graph, partial/generated declarations, platform context, overloads, interfaces, ambiguous names and multiple affected classes/methods. Neither changed-file count nor line count alone defines task difficulty.
- Test both a complete one-shot request and a bounded 2-3-prompt workflow. Internal tool calls and independent repeated sessions are not user follow-up prompts. Ten/twenty-turn sessions are outside this evaluation.
- Match final goals and acceptance conditions. Do not compare one-shot investigation only to multi-prompt implementation/validation. Report first-pass and final correctness, correction/rework and total time/input for each workflow.
- Directly readable source/settings are ordinary-tool routing controls, not semantic-backend defeat cases. Their cost can expose unnecessary adoption overhead without supporting a blanket Navlyn-is-slow conclusion.
- Follow observed excess input, misinterpretation, route failures, stale reuse and other risks to evidence-based fixes. Preserve failures; recording them alone is insufficient. Distinguish measured causes from hypotheses and client limitations.
- Use existing project builds/tests and independent task acceptance checks. Keep the runner small, pin source snapshots, retain failed attempts and distinguish environment/preparation failure from task performance. No large evaluation framework, mandatory Navlyn usage, unrealistic sessions, repeated full suites or blanket new configuration surface.
- Keep ordinary text search and semantic investigation complementary. A correct no-Navlyn route is desirable when semantics add nothing. Evaluate semantic assistance by avoided uncertainty/rework and completed real tasks, not by tool invocation rate.
