# v0.9.1 product and engineering plan

## Objective and current status

Make Navlyn economical to have available and useful when compiler evidence matters, while preserving selection correctness and ordinary-tool workflows. Treat the measured adoption penalty as a release-critical product problem. Reliability, installation, contracts, and delivery defects remain in scope independently of that problem.

The [self-review](../evals/v0.8.7-v0.9.0-self-review.md) and [0.9.1 evidence](../evals/v0.9.1-product-evidence.md) record both defects and limits. Product changes A–E and operational fixes G–K/O are implemented locally and verified at their changed boundaries. The bounded unforced comparison F is complete; it does **not** establish overall adoption savings. Per the release instruction, stop further model/optimization loops and release the useful reductions with this limitation visible. L/M ownership and context review reused existing coverage; N large-workspace measurement remains future work rather than a speculative rewrite. No package is published yet.

The default is an intentional MCP contract transition in 0.9.1: four tools and compact facts. Add `--surface full` for the previous 25 tools and full results. CLI JSON remains complete. This decision follows the user's instruction to address default adoption cost without preserving a mismatched product merely for conservatism. Setup, consumer probes, options, migration guidance, and release notes agree on the transition.

Do not solve discovery by replacing 25 tools with one equally large dispatcher schema, paginating a list clients still enumerate entirely, or assuming SDK 2 provides client-side deferred tool injection. Do not universally remove structured-content text fallback: [MCP compatibility guidance](https://modelcontextprotocol.io/specification/2025-06-18/server/tools#structured-content) recommends it. Reduce the common canonical result and examine actual client behavior before changing transport policy.

## Verification without restoring expensive gates

Use existing resolver component fixtures for qualified search, ambiguity, type-kind, and context behavior. Exercise actual stdio discovery and calls for focused/full surfaces, validation, result projections, and legacy text/structured content. Add meaningful contracts for retained identity, warning/limit semantics, and selected tool availability; avoid snapshots of every word or arbitrary minimum lengths. Test the changed package/setup boundary before a full delivery run.

Keep one integrated product run for materially changed product inputs, selected portable coverage on secondary OS jobs, and exact-main installation of the packed bytes. Use focused reruns after corrections. Reuse existing publication-recovery and skill-install lifecycle scripts. Do not add live model runs to ordinary CI, a new scoring harness, or redundant build/restore/pack passes. A cheap deterministic payload-size comparison may report growth, but smaller bytes cannot substitute for correctness or observed agent benefit.

For the bounded live check, use approximately three easy and three semantic tasks: literal/config/local-body work; overloaded binding across project/TFM context; interface/extension or generated/partial relationships; and one edit where a same-name target really creates risk. Derive exact signature/location/caller-set and edit-diff oracles independently of the agent answer. Preserve model/client version, actual reasoning configuration, clean source state, exposed schemas, selected skill, cold/warm session state, and raw calls. Counterbalance execution order; repeat only results whose variance or failure changes the decision. Avoid simultaneous conditions sharing a host when measuring latency.

Record total and uncached input, output tokens, complete task time, calls/retries, semantic correctness, exact edit diff, discovery bytes, canonical result bytes, and whether the client duplicates rendered content. Include time-to-first-use even when zero semantic calls are made. Character counts are not token counts. Do not claim monetary savings without corresponding pricing/usage evidence, or large-repository accuracy from a tiny sample.

## Order, release decision, and later work

1. Complete the low-cost reporting/routing/upgrade repairs and keep their verification separate from unimplemented runtime work. **Local initial work is complete.**
2. Implement focused discovery, sufficient compact facts, qualified intent, and valid-call guidance in narrow units; measure each changed boundary immediately.
3. In parallel with the design, inspect independent correctness and delivery paths listed above; land reproduced fixes without expanding an optimization into a large rewrite.
4. Run the bounded free-choice comparison on the actual proposed configuration. If it yields no measured benefit, record that limitation and stop; do not invent an attribution or prolong optimization. The adoption defect is not claimed resolved.
5. Reconcile documentation and run integrated/release checks once the proposed package inputs stabilize. Publish after implemented product fixes and final CI/packaged-consumer checks are ready; preserve the negative/limited observed evidence. This plan does not imply a release until publication finishes.

Later candidates, conditional on evidence: capability-aware client tool search/deferred loading; a small typed relationship composition API where model-turn latency dominates; incremental workspace-input tracking with preserved invalidation guarantees; configurable result section selection; and additional .NET domain facts only when actual tasks justify them. HTTP/OAuth/Apps/Tasks transports, another broad tool catalog, stronger runtime-proof claims, and a daemon redesign have no demonstrated need for this patch. Keep extension points narrow so a later feature does not impose cost on basic navigation.

## Audit disposition

L/M: reviewed query/candidate/source paths, AsyncLocal selection inheritance and retained selector TFM, input inventory, stable-load publication, retire/lease ownership and cancellation cleanup. Existing tests cover linked-source ambiguity/project filters, same-length edits/restored timestamps, add/delete/rename, ancestor config, reference and assets replacement, publication-boundary edits, canceled refresh, simultaneous retired leases, stale in-call edits, external process cleanup and invalid input/output limits. The full run passed these boundaries. New tests cover qualified container nonfallback, overload ambiguity, type-kind/record facts and focused/full stdio projections/paging/errors. No additional ownership rewrite was justified. Custom restore-file locations remain a documented manual-refresh limitation.

N: discovery/result sizes, complete-task costs, and one persistent session on the actual five-project/247-document repository were measured (cold summary 3.809 s, warm calls 70–76 ms). Total memory and larger multi-project scales remain unmeasured. The dominant observed penalty in the small interface task is additional model/tool turns and source inspection; millisecond warm-cache figures do not solve it. Large multi-project latency/memory instrumentation and incremental freshness optimization are deferred until a concrete workload warrants the cost. This is an explicit unmet research item, not a claim of large-workspace improvement.
