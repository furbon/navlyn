# Evidence boundaries

Read the particular boundary that affects the answer; these are not mandatory extra calls.

- **Identity and ambiguity:** confidence is selection evidence, not certainty. Preserve materially different overloads and containing types. Refine from available source, project, and framework context; ask only when intent remains unresolved. A candidate list does not authorize selecting its first entry.
- **Freshness:** candidate IDs describe an indexed workspace and can become invalid after edits or context changes. On rejection, reselect from current source if work must continue. A cache hit does not prove freshness or build success. Refresh when reported state or conflicting source justifies it.
- **Search bounds:** warnings, scope, partial results, and truncation qualify conclusions. A bounded empty result is not proof of absence. Obtain the missing evidence by narrowing, widening, or reading relevant text; client display clipping does not justify abandoning a requested task.
- **Compilation context:** the same linked file can have different bindings across projects/frameworks. Preserve the relevant context. Partial types can span files; generated source is compiler-visible evidence without establishing ownership or generator behavior.
- **Execution:** static calls, registrations, routes, options, handlers, EF models, and package usage do not establish runtime dispatch, effective configuration/authorization, database state, package compatibility, or production reachability. Test candidates are not tests executed. Use the appropriate ordinary tools for requested build, test, or runtime proof.
- **Failure and override:** respect explicit tool choices. If semantic tooling cannot load the needed context, perform useful ordinary inspection and distinguish text evidence from unresolved semantics. Do not invent successful tool results, silently switch targets, or repeatedly retry without new information.
